# Context: Uncle Quin Podcast EP.56 - "ออกแบบจากจุดใช้งาน & ศิลปะแห่งการเริ่มต้นด้วยฉากจบ (Interface Usability-First & Kierkegaard)"

Speaker 2: สวัสดีครับผู้ฟังทุกท่าน ขอต้อนรับเข้าสู่รายการ Uncle Quin EP.56 กับผม ลุงควิน และคุณพลอย Solo Tech Founder คนเก่งของเรา สวัสดีครับพลอย

Speaker 1: สวัสดีค่ะลุงควิน และสวัสดีแฟน ๆ รายการ Uncle Quin ทุกคนค่ะ สัปดาห์นี้พลอยอยากชวนคุยถึงช่วงเวลาที่หลายคนน่าจะเคยเจอเวลาทำโปรเจกต์ หรือเวลาตั้งเป้าหมายในชีวิต นั่นคืออาการ "ก้มหน้าก้มตาทำ ลุยแหลกไปเรื่อย ๆ แต่พอเงยหน้าขึ้นมาอีกที... อ้าว นี่เรากำลังทำอะไรอยู่? แล้วมันตอบโจทย์จริงไหม?"

Speaker 2: [laughs] ในหมู่วิศวกรซอฟต์แวร์ เราเจอกันประจำครับพลอย พอได้รับโจทย์มาปุ๊บ หลายคนรีบเปิด Editor แล้วกระโจนลงไปเขียนโค้ดทันที คิดอัลกอริทึมซับซ้อน ผูกลอจิกข้างในอย่างเมามัน ผ่านไปสองสัปดาห์ โค้ดภายในเขียนฉลาดมาก ลึกซึ้งมาก แต่พอจะเอามาเรียกใช้จริง หน้าตาฟังก์ชันกลับเละเทะ เรียกใช้ยาก พารามิเตอร์ส่งมั่วไปหมด จนเพื่อนร่วมทีม—หรือแม้แต่ตัวเราเองในอีกสามเดือนข้างหน้า—ต้องเกาหัวว่า "ฟังก์ชันนี้มันใช้ยังไงกันแน่?"

Speaker 1: ใช่เลยค่ะ ในมุม Product พลอยมักจะเห็นทีมสร้างฟีเจอร์ที่ซับซ้อนมาก แต่ไม่มีใครอยากใช้ เพราะตอนสร้าง ดันเอาแต่สนใจ "วิธีการข้างใน" มากกว่า "ประสบการณ์การเรียกใช้จริง (Developer Experience & Usability)"

Speaker 2: ถูกต้องครับ การหลงติดอยู่กับ Implementation Details หรือรายละเอียดเชิงเทคนิคข้างใน โดยไม่มองหน้าตาของ Interface ภายนอกก่อน เป็นสาเหตุอันดับต้น ๆ ที่ทำให้ทั้งโค้ดและชีวิตมนุษย์พังลงแบบเงียบ ๆ

Speaker 1: แล้วในมุมของ Software Architecture มีแนวปฏิบัติที่เข้ามาแก้ปัญหานี้อย่างไรคะลุงควิน?

Speaker 2: เรามีแนวคิดที่เรียกว่า Interface Usability-First หรือการออกแบบโดยให้ความสำคัญกับ "จุดสัมผัสของผู้เรียกใช้งาน" มาก่อนสิ่งอื่นใดครับ
ก่อนที่คุณจะเขียนโค้ดบรรทัดแรกข้างในฟังก์ชัน ก่อนที่คุณจะคิดเรื่องลูป เรื่องฐานข้อมูล หรือประสิทธิภาพ ให้คุณเปิดไฟล์ว่าง ๆ แล้วลองเขียน "โค้ดตัวอย่างที่กำลังเรียกใช้ฟังก์ชันนั้น" ดูก่อน:
ฟังก์ชันนี้ควรชื่ออะไร ถึงจะสื่อความหมายได้ทันทีโดยไม่ต้องเปิดอ่านคู่มือ?
พารามิเตอร์ที่ต้องส่งเข้าไป มีกี่ตัว? มันเยอะเกินไปจนสร้างภาระทางความคิดไหม?
ผลลัพธ์ที่ตอบกลับมา มันสมเหตุสมผลและเอาไปใช้งานต่อง่ายหรือเปล่า?

Speaker 1: อ๋อ! มันคือการสวมหมวกของ "คนใช้งาน (Caller / Consumer)" ก่อนที่จะสวมหมวกของ "คนสร้าง (Implementer)" ใช่ไหมคะ?

Speaker 2: ถูกต้องที่สุดครับ เหมือนนักออกแบบสวิตช์ไฟ คุณต้องตัดสินใจก่อนว่า สวิตช์ควรอยู่ตรงระดับไหนของผนัง กดง่ายไหม เสียงคลิกชัดเจนไหม ก่อนที่คุณจะลงมือเดินสายไฟและต่อแผงวงจรข้างในผนัง
ถ้า Interface มันออกแบบมาดี เข้าใจง่าย และให้ความรู้สึกเป็นธรรมชาติ (Ergonomic) ต่อให้ข้างใน Logic จะซับซ้อนแค่ไหน การใช้งานและการดูแลรักษาก็จะราบรื่นมาก แต่ถ้า Interface มันแย่ตั้งแต่แรก ต่อให้ข้างในเขียนล้ำเลิศแค่ไหน มันก็คือระเบิดเวลาที่ไม่มีใครอยากแตะต้อง

Speaker 1: พอฟังเรื่องนี้แล้ว พลอยนึกถึงแนวคิดทางปรัชญาที่ลุงควินชอบยกมาคุยบ่อย ๆ เลยค่ะ เรื่องที่ว่ามนุษย์เรามักจะสับสนกับทิศทางของเวลา

Speaker 2: ใช่เลยครับ นักปรัชญาอัตถิภาวนิยมชาวเดนมาร์กอย่าง Søren Kierkegaard เคยเขียนประโยคอมตะไว้ในสมุดบันทึกของเขาว่า:
"Life can only be understood backwards; but it must be lived forwards."
(ชีวิตจะเข้าใจได้ก็ต่อเมื่อมองย้อนกลับมาเท่านั้น แต่ในความเป็นจริง เราต้องใช้ชีวิตก้าวไปข้างหน้า)

นี่คือปมขัดแย้ง (Paradox) ขั้นพื้นฐานของมนุษย์ครับ เวลาเราก้าวไปข้างหน้าในแต่ละวัน เราต้องเจอกับม่านหมอกแห่งความไม่แน่นอน ข้อมูลที่ไม่ครบถ้วน ความวุ่นวายของอารมณ์ และรายละเอียดปลีกย่อยที่ถาโถมเข้ามา เหมือนวิศวกรที่กำลังจมอยู่ใน Function Body อันยุ่งเหยิง

Speaker 1: แล้วเราจะเชื่อมโยงสองสิ่งนี้เข้าด้วยกันได้อย่างไรคะ? ในเมื่อชีวิตจริงเราไม่สามารถ "ย้อนเวลากลับมาจากอนาคต" ได้จริง ๆ?

Speaker 2: สิ่งที่เราทำได้คือการ "จำลองการมองย้อนกลับ (Simulated Backward Perspective)" ด้วยการออกแบบ Interface ปลายทางไว้ล่วงหน้าครับ
หลักการนี้ตรงกับนิสัยที่สองในหนังสือ The 7 Habits of Highly Effective People ของ Stephen Covey นั่นคือ "Begin with the End in Mind" (เริ่มต้นด้วยจุดจบในใจ)
ก่อนที่คุณจะกระโจนลงไปใช้ชีวิตในแต่ละวัน แต่ละโปรเจกต์ หรือแต่ละความสัมพันธ์ ให้ถามตัวเองก่อนว่า "หน้าตาของผลลัพธ์สุดท้ายที่เราต้องการ (The Interface Contract)" คืออะไรกันแน่?
ในงานนี้ นิยามของความสำเร็จไม่ใช่การทำทุกอย่าง แต่คือการส่งมอบผลลัพธ์รูปธรรมชิ้นไหน?
ในความสัมพันธ์นี้ Interface ของเราคือความเข้าอกเข้าใจและพื้นที่สบายใจใช่หรือไม่?
เมื่อ Interface ปลายทางถูกตรึงไว้อย่างชัดเจนและงดงามแล้ว ต่อให้จังหวะที่เรากำลังลงมือใช้ชีวิตจริง (The Implementation Details) จะต้องเจอกับความเลอะเทอะ บั๊ก หรืออุปสรรค เราก็จะไม่หลงทิศ เพราะเรารู้ว่ากำลังประกอบชิ้นส่วนทั้งหมดเพื่อไปประกอบเข้ากับ Interface ใด

Speaker 1: ฟังดูเหมือนเป็นการติดประภาคารนำทางให้ชีวิตเลยค่ะ แล้วในทางปฏิบัติ ถ้าคนทำงานหรือผู้ฟังอยากฝึกฝนทักษะการคิดแบบ Interface Usability-First ในชีวิตประจำวัน ลุงควินมีเฟรมเวิร์กแนะนำอย่างไรบ้างคะ?

Speaker 2: ผมขอสรุปเป็น 3 ขั้นตอนในการออกแบบสถาปัตยกรรมชีวิตแบบ Interface-First ครับ:
Draft the Call-Site First (เขียนโค้ดตอนเรียกใช้ก่อน): เวลาเริ่มโปรเจกต์ใหม่ ไม่ว่าจะเป็นการทำธุรกิจ การเขียนหนังสือ หรือการปรับเปลี่ยนพฤติกรรมตัวเอง อย่าเพิ่งรีบคิดเรื่องกระบวนการภายในที่ยุ่งยาก ให้ร่างภาพ "ประสบการณ์ตอนนำไปใช้จริง" ก่อน เช่น ถ้าเป็นธุรกิจ ให้เขียนภาพวันแรกที่ลูกค้าได้รับของแล้วยิ้ม ถ้าเป็นการพัฒนาตัวเอง ให้นึกภาพว่ากิจวัตรตอนเช้าที่ทำแล้วรู้สึกเบาสบายหน้าตาเป็นอย่างไร
Optimize for Mental Ergonomics (ลดภาระทางความคิด): Interface ที่ดีต้องไม่ซับซ้อนจนคนเรียกใช้ต้องปวดหัว ชีวิตเราก็เหมือนกัน อย่าสร้างกติกาหรือเงื่อนไขให้ชีวิตตัวเองเยอะเกินไปจนกลายเป็นอัมพาตในการลงมือทำ ตั้งกติกาง่าย ๆ ชัดเจน เช่น "ออกกำลังกายวันละ 15 นาที" แทนที่จะตั้งระบบซับซ้อนที่ต้องตรวจวัด 20 ตัวแปร
Decouple What from How (แยกแยะ "อะไร" ออกจาก "อย่างไร"): รักษา Interface (เป้าหมายและคุณค่าหลัก) ให้มั่นคง แต่อนุญาตให้ Implementation (วิธีการ กลยุทธ์ แผนสำรอง) สามารถยืดหยุ่น ปรับเปลี่ยน และเขียนใหม่ได้ตลอดเวลาตามสถานการณ์จริง

Speaker 1: ขอสรุป 3 ข้อคิดสำคัญสำหรับ Uncle Quin EP.56 วันนี้ค่ะ:
Think Like the Caller: สวมหมวกของคนที่ต้องมารับช่วงต่อหรือใช้งานจริง ก่อนที่จะจมลงไปในความสนุกของการสร้างกลไกที่ซับซ้อน
Design the End, Live the Middle: ออกแบบภาพปลายทางและความหมายของชีวิตไว้ล่วงหน้า เพื่อให้เรามีหลักยึดในวันที่ต้องลุยผ่านรายละเอียดที่ยุ่งเหยิงในแต่ละวัน
Simplicity is the Ultimate Sophistication: สถาปัตยกรรมที่ดีที่สุด ทั้งในซอฟต์แวร์และชีวิต คือสถาปัตยกรรมที่เรียบง่าย ชัดเจน และใช้งานได้จริงโดยไม่สร้างความทุกข์ระทมให้ผู้ใช้งานค่ะ

Speaker 2: สรุปได้ลึกซึ้งและเฉียบคมมากครับพลอย ขอบคุณมากครับ และขอขอบคุณผู้ฟังทุกท่านที่ร่วมสำรวจสถาปัตยกรรมชีวิตไปพร้อมกับเราใน Uncle Quin ก่อนเริ่มก้าวเดินในวันพรุ่งนี้ ลองหยุดสักนิดเพื่อสเก็ตช์ภาพฉากจบที่คุณอยากเห็น แล้วค่อยออกเดินทางนะครับ สำหรับตอนนี้ สวัสดีครับ
